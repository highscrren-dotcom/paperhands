# Консенсус толпы — гипотеза закрыта

Задание из `TASK.md`: довести фильтр входа по согласию толпы до walk-forward —
полная сетка правил, детектор нерабочих месяцев, схема «параметры с прошлого →
торговля на следующем». Критерии приёмки: PnL > 0, на сделку > 0.4 %, ≥10 сделок
в месяц, плюсовых месяцев > 50 %, превосходство над всеми тремя контролями,
эффект на двух символах.

**Результат: гипотеза не подтверждена. Причина найдена — весь эффект был
заглядыванием вперёд.**

## 1. Репликация — числа сошлись

Мой конвейер воспроизвёл `consensus_all.py` на тех же 67 месяцах BTCUSDT
(окно 7.5 / 1.5 / 11 сут / 2):

| направление | вариант | мой прогон | у тебя |
|---|---|---|---|
| SHORT | все | −624.6 % / 1356 сд | −616.2 % / 1356 сд |
| SHORT | консенсус | −158.9 % / 536 сд | −154.2 % / 536 сд |
| LONG | все | −952.8 % / 2576 сд | −952.8 % / 2576 сд |
| LONG | консенсус | −744.9 % / 2091 сд | −744.9 % / 2091 сд |

Счётчики сделок совпали до штуки, LONG совпал точно. Расхождение по SHORT
(8 п.п. из 620) — разные снапшоты, на выводы не влияет.

## 2. Где дыра

В `consensus_all.py` и `entry_filter.py` окно согласия считается так:

```python
same = sum(1 for o in ts if abs(o['entryTimestamp'] - t['entryTimestamp']) <= W
           and o['direction'] == D)
```

`abs(...) <= W` — окно **симметричное**, `[t − W, t + W]`. В счёт согласия
попадают идеи, опубликованные **после** входа. На момент сделки их не
существует: фильтр знает, что толпа будет писать в ближайшие 24 часа.

Причинная версия — то же самое, но окно `[t − W, t]`:

| направление | источник согласия | окно | сделок | PnL | на сделку |
|---|---|---|---|---|---|
| SHORT | сделки | ±24 ч (твоё) | 536 | −158.9 % | **−0.296 %** |
| SHORT | сделки | [−24 ч, 0] | 701 | −321.8 % | **−0.459 %** |
| SHORT | идеи | ±24 ч | 462 | −91.2 % | −0.197 % |
| SHORT | идеи | [−24 ч, 0] | 635 | −352.1 % | −0.555 % |
| LONG | сделки | ±24 ч | 2091 | −744.9 % | −0.356 % |
| LONG | сделки | [−24 ч, 0] | 2062 | −811.4 % | −0.394 % |

Без фильтра SHORT даёт **−0.461 %** на сделку. Причинный консенсус даёт
**−0.459 %** — ровно столько же. Улучшение с −0.461 до −0.296 целиком
создаётся будущими идеями. У LONG причинная версия хуже базы (−0.394 против
−0.370).

Экономический смысл эффекта тоже понятен: знать, что в ближайшие сутки толпа
набежит в ту же сторону — это знать про будущий приток внимания, а он сам по
себе двигает цену. Торговать этим нельзя.

## 3. Полная сетка (шаг 1 ТЗ) — на причинном окне

108 комбинаций: W ∈ {6, 12, 24, 48, 72} ч × правила {same>opp, перевес ≥ 1/2/3/4/6,
доля ≥ 0.55/0.6/0.7} × два направления, BTCUSDT, все 67 месяцев,
согласие считается по **идеям** (все мнения толпы, не только торгуемые).

Положительных ячеек — 5 из 108, все на обрезках выборки:

| напр | W | правило | сделок (из базы) | на сделку | плюсовых месяцев |
|---|---|---|---|---|---|
| LONG | 6 ч | перевес ≥6 | 39 из 2576 (1.5 %) | +0.758 % | 3 / 67 |
| SHORT | 48 ч | перевес ≥6 | 97 из 1356 (7 %) | +0.639 % | 8 / 66 |
| SHORT | 24 ч | перевес ≥6 | 41 (3 %) | +0.318 % | 5 / 66 |
| SHORT | 48 ч | перевес ≥4 | 174 (13 %) | +0.115 % | 11 / 66 |
| LONG | 6 ч | перевес ≥4 | 139 (5 %) | +0.109 % | 14 / 67 |

Это ровно тот случай, про который написан твой методический пункт 7: фильтр,
отсекающий 95 % входов, выглядит лучшим потому, что не торгует. Ячейки не
образуют области — разные W, разные K, соседи по сетке отрицательные. При 108
проверках 5 положительных — ожидаемый шум.

## 5. Walk-forward (шаг 3) — решающий

Схема ТЗ: (W + правило) подбираются на месяцах [M−12, M−1], торговля считается
на M. Чтобы фильтр не «выигрывал» отказом от торговли, при обучении требуется
оставлять ≥15 % сделок.

| напр | тестовых мес | плюсовых | сделок | выбранный фильтр | без фильтра | случайный фильтр |
|---|---|---|---|---|---|---|
| SHORT | 45 | 22 / 45 | 388 | **−0.488 %** | −0.402 % | **−0.090 %** |
| LONG | 55 | 19 / 55 | 1451 | **−0.475 %** | −0.346 % | −0.588 % |

По SHORT выбранный фильтр хуже и «торговать всё», и **случайного фильтра**.
По LONG хуже базы. Ни один критерий приёмки не выполнен: PnL < 0, на сделку
< 0.4 %, плюсовых месяцев 49 % и 35 %, все три контроля не побеждены.

Выбор нестабилен — что подбирается на обучении, видно по последним месяцам:
`feb_2026: W72/same>opp → mar_2026: W6/перевес≥2 → apr_2026: W48/доля≥0.6 →
may_2026: W48/same>opp → jun_2026: W6/перевес≥2`. Параметр скачет каждый месяц,
то есть на обучающем окне побеждает шум.

## 6. Детектор нерабочего месяца (шаг 2)

Признаки, доступные до входа, против PnL текущего месяца (BTCUSDT, 66 переходов):

| признак | корреляция |
|---|---|
| PnL предыдущего месяца в том же окне | **+0.223** |
| перекос ленты предыдущего месяца | +0.074 |
| число сделок предыдущего месяца | −0.070 |
| число идей предыдущего месяца | −0.066 |

Лучший признак — прошлый PnL, r = +0.223, слабо. И главное: гипотеза про
перекос переворачивается. У «мёртвых» месяцев (PnL < −100 %) средний перекос
ленты **+0.279**, у прибыльных **+0.400** — то есть перед плохими месяцами толпа
менее однобока, а не более. Работающего детектора из этих признаков не выходит.

## Что это значит

Направление «консенсус толпы» закрывается так же, как закрылся «отбор авторов» —
и по той же причине: в ретроспективе фильтр видел то, чего в реальном времени не
существует. Разложение убытка на сигнал и издержки (+101.5 % против −52.5 % в
медианном окне) остаётся верным, но консенсус эту разницу не забирает.

Что осталось непроверенным и по-прежнему осмысленно:

1. **Реальные издержки** (твой пункт 4 в непроверенных). Это единственный рычаг,
   который бьёт по причине, а не по симптому: сигнал есть, он меньше 0.4 % на
   круг. Мейкерские лимитки дают 0.02 % вместо 0.1 % комиссии — при 385 входах в
   месяц это меняет знак у части окон. Требует перегона симулятора с другими
   `CC_PERCENT_FEE`/`CC_PERCENT_SLIPPAGE`, в датасете этих данных нет.
2. **Отбор авторов по PnL** — не по `hitRate`. Твой r = +0.011 меряет
   переносимость `hitRate` месяц-к-месяцу; я мерил другое: отбор топ-3 авторов по
   их PnL за прошлые 12 месяцев на фиксированном правиле. Детали ниже.

## Про отбор авторов: наши результаты не противоречат друг другу

У меня на правиле **холд 14 сут / лок 5 % / стоп 10 % / трейлинг 5 %** отбор
топ-3 по PnL прошлых 12 месяцев (порог ≥10 идей) даёт **+0.703 % на сделку**
сверх поля тех же символов, 824 сделки, лифт положителен во всех пяти годах
(+0.36 / +0.78 / +0.67 / +0.91 / +1.24). Плацебо с перемешиванием ярлыков авторов
внутри символа — p = 0.000, с перемешиванием рейтинга обучения — p = 0.023.
Соседи по сетке: при lock = 5 % положительны все 15 комбинаций стоп 8–10 ×
трейлинг 4–5.

Это не спорит с твоими числами:

- твой `r = +0.011` — про перенос **hitRate**, а `hitRate` на краю сетки прямо
  противоречит деньгам (твой же пункт 3 методики);
- твой `who_in_window.py` (0 из 21 280 окон прибыльны) считает **весь пул** из
  37 авторов; я не торгую пул, я беру верхушку из трёх;
- твой `pnl_oos_report.py` подбирает **персональное окно** каждому автору —
  у меня окно одно для всех, подбираются только авторы.

Оговорки честные: правило стоит на краю сетки (lock 5 % и trail 5 % — максимумы
осей, при lock 4 % знак переворачивается), проверено ~130 связок правило × отбор,
и всё это на бэкфиле. **Первое, что стоит сделать: продлить оси `lock` и `trail`
за 5 %.** Если находка настоящая — эффект продолжится за краем; если нет —
оборвётся, и направление закроется тоже.
