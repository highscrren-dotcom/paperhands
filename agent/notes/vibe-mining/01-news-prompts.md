## Приёмы, которые стоит забрать (event-driven SKILL.md)

1. **Якорёная непрерывная шкала вместо бинарного long/short.** Их промпт даёт
   -1.0…+1.0 с ПРИМЕРАМИ на каждой ступени: «1.0 = earnings far above expectations,
   major favorable policy; 0.5 = slightly above expectations; 0.2 = mildly bullish;
   0.0 = neutral; -1.0 = accounting fraud, black-swan». Якоря стабилизируют скоринг
   между вызовами — у нас confidence сейчас ничем не заякорен (модель выдаёт
   0.6-0.9 «на глаз»).
2. **Таксономия событий** (`earnings/macro/policy/sentiment/insider/technical_break`)
   с типичной длительностью эффекта (1-5д / 5-20д / 20-60д…). Для нас: наш `class`
   (etf/fomc/crash-rally/regulation) — это класс ЗАПРОСА Tavily, а не события;
   LLM-поле event_type было бы честнее и даёт pump-anomaly доп. разрез.
3. **«Knowable date», не дата события** — публикация после закрытия → следующий
   торговый день; в бэктесте строго `event_date <= trade_date`. Это ровно канон
   автора (publishedAt + getSignal(when)) — подтверждение, что наш инвариант
   общепринят. Крипта 24/7 — сдвиг «после закрытия» нам не нужен.
4. **Дедуп события, не url**: одна новость от многих источников → дедуп по
   `(date, event_type)` или усреднение скоров. У нас дедуп только по url — одна
   и та же новость с 4 доменов войдёт 4 раза. Для НАШЕЙ задачи это фича, не баг:
   домен = псевдо-канал, pump-anomaly сам оценит каждый домен. Но помнить при
   интерпретации: «4 сигнала» может быть одним событием.
5. **Sentiment drift**: скоринг дрейфует при смене промпта/версии модели —
   промпт зафиксировать, рекалибровать регулярно. Для нас: писать в аудит
   `promptVersion` + `model` (v1 уже пишет model; версии промпта нет).
6. **Event sparsity — не заполнять дыры**: большинство дней без событий, сигнал 0 —
   это норма, не выдумывать данные. Совпадает с нашим «87% отсев = фильтр шума».
7. **Time decay** exp(-0.1·days) — не для классификатора, а для потребителя
   сигнала; у нас этим потребителем будет pump-anomaly/getLast4HourSignal — decay
   не наша забота на этапе датасета.

## Из social-media-intelligence (§3.1, §7)

- Каскад дешёвое→дорогое: VADER/FinBERT всё, LLM только там, где confidence<0.6.
  Нам с ~десятками новостей/день не нужно, но идея «LLM как последняя инстанция»
  запомнена.
- Их LLM-промпт заставляет отдавать `reason` одним предложением вместе со score —
  дёшево и даёт аудиторский след + слегка дисциплинирует модель (см. v2).
- Подача тикера в промпт отдельным полем контекста (`Ticker: X`), когда известен.
- §7: social-sentiment IC ≈ 0.03-0.06 — «supporting factor, not primary»;源-качество
  (source-quality scoring) обязательно — ровно наш channelScore-замысел.

## Из sentiment-analysis

Для классификатора — ничего (это макро-дашборд сентимента, реверс-индикаторы).
Единственное: композитный скор из независимых измерений с фиксированными весами —
философия «не верь одному индикатору», нам не в тему датасета.

## Чего у них НЕТ (наши инварианты сильнее)

- Привязки к активу в промпте event-driven нет вообще — скорят «новость → влияние
  на цену ИНСТРУМЕНТА», инструмент задан заранее (CSV на бумагу). Наш two-step
  «сначала symbol, потом direction» — сильнее, оставляем.
- Строгого JSON-format нет (у них «output one number only») — наш format-схема +
  jsonrepair надёжнее.
- Binance-листинг-гейта нет (у них нет биржевой привязки вообще).
