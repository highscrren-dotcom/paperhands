## Подтверждение механизма (словами автора)

Порядок эмиссии закрытий детерминирован (`StrategyConnectionService`,
`CALL_SIGNAL_EMIT_FN`):

```
closed-событие:
  1. await signalBacktestEmitter.next(tick)  → подписчик Storage ПИШЕТ строку closed
  2. await signalEmitter.next(tick)           → heat-тик HeatMarkdownService
```

Первый close-тик прогона внутри heat-тика делает `await storage.waitForInit()` —
ленивый singleshot-реплей истории закрытых из Storage (`StorageBacktest.list()` /
`StorageLive.list()`). К этому моменту шаг 1 **уже записал этот самый close**,
поэтому реплей добавляет его в статистику; затем штатный `addSignal(data)` того
же тика добавляет его второй раз. Seen-set внутри реплея дедупил только строки
истории между собой.

Симптомы, все объяснены:
- ровно **+1 сделка** в каждом прогоне (задваивается только событие-инициатор —
  первый close; последующие приходят при уже завершённом singleshot);
- фантом — **точный дубль первого закрытия** (совпадение PnL до ~1e-15: тот же
  объект строки);
- `storage/backtest` на диске пуст — лента Storage живёт в памяти процесса,
  реплей читает её же;
- расхождение только в heatmap-агрегате (`status_info`), а
  `dump/report/backtest.jsonl` считает по самой ленте событий и потому верен.

## Исправление (в репозитории: dba88cb — HeatMarkdownService.ts +40/-3)

`HeatmapStorage` получил **consume-once набор `replayedIds`**:
- `waitForInit` запоминает id каждой строки, добавленной реплеем истории;
- `addSignal` при доставке события с таким id **глотает его ровно один раз**
  (`Set.delete` на попадании) — это и есть событие-инициатор, уже посчитанное из
  истории; набор при этом очищается, память не растёт.

Намеренно НЕ изменилось:
- повторные id в ленте событий по-прежнему считаются отдельно (глобального
  дедупа по id нет — закреплённый спеками контракт; один id на разных символах
  не склеивается);
- restart-реплей жив (переживание рестарта, включая live);
- `report/dump/backtest.jsonl` не трогали — он и был верным.
