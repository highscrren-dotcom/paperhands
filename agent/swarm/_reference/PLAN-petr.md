> текст. Оригинал у владельца. ЭТОТ план — канон стенда, наш слой — аддитивен.

Цель: применить Simulator на 12 месяцах отдельными папками, выбрать
множество авторов (рой), ранжировать букашек по числу ПРИБЫЛЬНЫХ месяцев,
и в эксплуатации единовременно смотреть последние рекомендации всех
допущенных авторов, решая по весу — перевешивает LONG или SHORT.

Доктрина неизменна: движок оценивает каждую букашку строго изолированно,
рой и его веса — юзерспейс. Никаких новых механик в движке этот план не
требует: только `Simulator.run`, `Simulator.test` и арифметика поверх
их дампов.

---

## Этап 0 — раскладка данных на жёсткий диск

Один скрипт (`tools/split_months.mjs`) режет полный годовой фид на месяцы
по UTC-границам (`ts >= начала месяца && ts < начала следующего`) и
раскладывает папки. Никаких молчаливых дефолтов: скрипт принимает путь к
полному фиду и год явно.

```
янв_2025
фев_2025
мар_2025
апр_2025
май_2025
июнь_2025
июль_2025
август_2025
сентябрь_2025
октябрь_2025
ноябрь_2025
декабрь_2025
```

В каждой папке структура (ровно такая, ничего лишнего):

```
assets
|_______tv_ideas.jsonl   // идеи МЕСЯЦА за месяц, уже обрезанные
src
|_______index.mjs        // тренировка, Simulator.run
|_______test.mjs         // тест, Simulator.test
dump
|_______train.json       // дамп результата тренировки
|_______test.json        // дамп результата теста
```

Гарантии этапа:
- каждая идея попадает ровно в один месяц (по `ts`, UTC);
- формат строки — тот же контракт `ISimulatorIdea`
  (`id/ts/symbol/direction/author`), валидация до записи;
- сумма строк по 12 файлам == числу строк исходного фида (проверка
  скриптом, расхождение — громкая ошибка);
- кеш свечей общий на все папки (persist cache движка) — данные биржи
  скачиваются один раз.

## Этап 1 — точка канонизируется ОДИН раз

Чтобы месяцы были сравнимы между собой, правило игры фиксируется до
начала прогонов и не перевыбирается ни для одного месяца:

```json
POINT = {
  "hardStopPercent": 3,
  "trailingTakePercent": 4,
  "holdMinutes": 4320,
  "minAuthorTrack": 2,
  "minAuthorHitRate": 0.5,
  "profitLockPercent": 0,
  "authorMetric": "<выбрать экспериментально>"
}
```

**`authorMetric` НЕ предрешён — его нужно выбрать экспериментально** из
всех пяти: `"close" | "reach" | "retain" | "pnl" | "trail"`. "close" в
июньских выстрелах — факт одного месяца одной ленты, не закон. Выборочный
эксперимент: на 2–3 калибровочных месяцах (они после этого сгорают для
теста — в walk-forward этапа 3 не участвуют) прогнать этап 2 по всем пяти
метрикам параллельно, собрать пять вариантов помесячных треков и выбрать
метрику, чей рой (а) стабильнее по числу выживших авторов от месяца к
месяцу и (б) даёт лучший OOS на калибровочном хвосте. Выбранная метрика
фиксируется в POINT — и с этого момента правило неизменно: смена метрики
(как и любого поля точки) = перегон всех 12 месяцев заново, частичная
замена запрещена. Остальные поля точки — действующий замороженный
кандидат тюна.

## Этап 2 — тренировка месяца (`src/index.mjs`)

`Simulator.run` по `assets/tv_ideas.jsonl` месяца. Ключевое требование —
PnL букашки БЕЗ взаимодействия: общий прогон делит один слот на всех, и
занятый слот одного автора съедал бы идеи другого. Поэтому:

1. один общий прогон месяца — для справочных цифр и trainedStats;
2. затем ЦИКЛ ПО АВТОРАМ: для каждого логина с >= 1 идеей месяца —
   отдельный `Simulator.run` только его идей на канонической точке
   (оси зеркалят POINT одноточечно). Слот автора — его собственный,
   букашки друг друга не видят.

`dump/train.json` — сырые данные, без производных метрик:

```json
{
  "month": "янв_2025",
  "point": { ...POINT... },
  "authors": [
    { "author": "TradingShot", "ideas": 14, "trades": 6,
      "pnlPercent": 4.12, "exitReasons": { ... } },
    ...
  ]
}
```

Прибыльный месяц автора: `pnlPercent > 0` (строго больше; ноль и минус —
проигранный). Автор без сделок за месяц (все идеи съедены дедупом или
без свечей) месяц НЕ играет — он не выиграл и не проиграл, месяц не идёт
в его трек.

## Этап 3 — тест месяца (`src/test.mjs`) — walk-forward по месяцам

Месяц M тестируется роем, собранным ТОЛЬКО на месяцах < M (первый месяц
теста — не раньше, чем накопится минимальный трек, см. этап 4):

- `authorStats` для `Simulator.test` — помесячный трек роя как есть:
  `{ author, ideas: сыгранныеМесяцы(<M), hits: выигранныеМесяцы(<M) }`;
- точка — каноническая (этап 1), баны перевыводятся движком из
  замороженных чисел: `ideas >= minAuthorTrack`,
  `hits/ideas >= minAuthorHitRate`; невиданные авторы забанены;
- идеи — `assets/tv_ideas.jsonl` месяца M, целиком (это и есть хвост,
  которого рейтинг не видел);
- `dump/test.json` — полный `ISimulatorTestResult` как есть.

Это 12 честных OOS-выстрелов подряд: каждый месяц торгуется списком,
который знал только прошлое.

## Этап 4 — рейтинг роя (агрегация)

Скрипт (`tools/swarm_rank.mjs`) читает 12 `dump/train.json` и строит
`swarm.json`:

```json
[
  { "author": "TradingShot", "months": 9, "wins": 6 },
  { "author": "MasterAnanda", "months": 11, "wins": 5 },
  ...
]
```

- `months` — сколько месяцев букашка сыграла (были сделки);
- `wins` — сколько из них закрыла в плюс;
- никакой склейки, никаких сглаживаний, только сырые целые числа.

Допуск в рой — та же бан-арифметика, что везде: не доказал — забанен.
Пороги (например `months >= 3`, `wins/months >= 0.5`) — прикладная
константа юзерспейса, задаются явно в конфиге скрипта.

## Этап 5 — эксплуатация: единовременный снапшот роя

В момент времени T (`tools/swarm_vote.mjs`):

1. взять ПОСЛЕДНЮЮ рекомендацию каждого допущенного автора в скользящем
   окне `holdMinutes` точки (72h): идея старше окна — голос истёк, автор
   молчит; NEUTRAL — молчит;
2. вес голоса автора = `wins` (сырое число выигранных месяцев; не доли,
   не Вильсон — целые месяцы);
3. `W_long = сумма весов авторов с активным LONG`,
   `W_short = сумма весов авторов с активным SHORT`;
4. вердикт: `W_long > W_short` → LONG, `W_short > W_long` → SHORT,
   равенство (включая 0 == 0) → FLAT, сделки нет.

Голосование живёт целиком в юзерспейсе — движок об этом слое не знает и
знать не должен (в нём взаимодействие авторов вырезано намеренно, см.
BREAKING.md §1).

## Этап 6 — верификация вердиктов

Прежде чем верить снапшотам — прогнать его исторически: пройти по хвосту
года (месяцы, не участвовавшие в накоплении рейтинга голосующих) с шагом
в час, на каждом шаге взять вердикт этапа 5 и сверить с фактическим
движением цены на горизонте `holdMinutes`. Точность выше монетки на
объёме сотен снапшотов — сигнал жив; нет — рой на этой ленте не
складывается, и это тоже ответ.

## Порядок работ

1. `tools/split_months.mjs` + раскладка 12 папок, проверка сумм строк.
2. Шаблоны `src/index.mjs` / `src/test.mjs` (одинаковые для всех папок,
   различие — только путь к своим assets; копипаста намеренная — папка
   читается линейно).
3. Прогон этапа 2 по 12 месяцам (фоном, кеш свечей общий).
4. `swarm_rank.mjs` → `swarm.json`, выбор порогов допуска.
5. Прогон этапа 3 (12 OOS-выстрелов), честный отчёт по каждому.
6. `swarm_vote.mjs` + верификация этапа 6.
